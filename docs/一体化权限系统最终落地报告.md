### 6.2 本轮真实修复（SSRF blocker 的根因）

`internal/application/service/user.go:1713` 的 `newOIDCHTTPClient()` 用 `secutils.NewSSRFSafeHTTPClient`，对 loopback / private IP 全部 block：

```
outbound request blocked by SSRF policy: SSRF validation failed: hostname 127.0.0.1 is restricted
```

**修复（最小、最安全）**：`introspectGatewayExchangeToken()` 改用普通 `http.Client{Timeout:10s}`：

- introspection URL 是 env 配置的内部 Gateway，不是用户输入
- URL 形状 + scheme 白名单（http/https）作为 defense-in-depth
- 显式注释解释：为什么此处绕开 SSRF（trusted operator config）
- 文件位置：`internal/application/service/user.go:1422-1477`

同时清理两轮调试期留下的 `[DBG-EXCH] step=...` 打印（共 11 处，全部移除；OIDC 路径的 1 处重命名为 `[DBG-OIDC]`，作为生产 trace 保留）。改动：

- 净删调试输出 11 行
- 新增 URL 形状校验 6 行
- 净增代码：约 4 行（含注释约 15 行）

## 八、生产化加固续（2026-08-31 第五轮新增）

### 8.1 Gateway dev-mode crash 根因 + 修复

**根因**：`services/casdoor-resource-gateway/src/index.ts:5040` 原代码：

```ts
export const server = createServer((req, res) => { void handle(req, res); });
```

`handle()` 返回 Promise；`void` 吞掉结果。Node ≥15 在 `--unhandled-rejections=strict`（默认）下，任何 `Promise` rejection 都会终止进程。`handle()` 内部 handler 自身 catch 各类错误并写 JSON 响应，但仍有边界情况（如 socket 已关闭、write 失败、未预期的异步异常）会触发 unhandled rejection。

**修复**：把 `void` 改成 `.catch()`：

```ts
export const server = createServer((req, res) => {
  handle(req, res).catch((error: unknown) => {
    const message = error instanceof Error ? error.stack ?? error.message : String(error);
    console.error("[gateway] unhandled rejection in request handler:", message);
    if (!res.headersSent) {
      try {
        res.statusCode = 500;
        res.setHeader("content-type", "application/json");
        res.end(JSON.stringify({ status: "error", code: "INTERNAL_ERROR", message: "unexpected gateway failure" }));
      } catch {
        // socket may already be closed; nothing more we can do
      }
    }
  });
});
```

**实测回放**：连续发送 80+ 个请求（含 20 次正常 exchange + 20 次 introspect + 20 次 refresh + 20 次故意 401），Gateway 全程 PID 不变，/healthz 持续返回 200。修复前每次 ~1-2 个请求后进程退出。

### 8.2 JTI replay 防护（轻量版）

新增 `weknoraJtiCache: Map<jti, { subject, expiresAt }>` + `weknoraSubjectJtis: Map<subject, Set<jti>>` 两个内存索引：

| 触发点 | 行为 |
|---|---|
| `handleWeKnoraTokenExchange` issue 时 | `rememberWeKnoraJti(jti, subject, exp)` — 100 次插入后做一次 lazy expiration cleanup |
| `handleWeKnoraTokenRefresh` issue 时 | 同上（新 jti 入缓存，旧 jti 仍可 introspect，sliding window 保留） |
| `handleBackchannelLogout` revoke 时 | `flushWeKnoraJtisForSubject(subject)` — 删除该 subject 全部 jti，返回 `{..., flushedJtis: <n>}` |
| `introspect` 路径 | 不查 jti（合法 WeKnora 每请求都调 introspect，单次签名 token 可被多次验证）|

**为什么不是严格"seen-once"**：
- WeKnora `validateGatewayExchangeToken` 在每个 incoming request 都调 Gateway introspect
- 同 token 在 5 min TTL 内会被 introspect 数十~数百次（长会话）
- 严格"seen-once"会让合法 retry 也失败 — 反而破坏可用性
- UUID v4 冲突概率 ~2⁻¹²²，已足够保障 jti 唯一
- 真正威胁面是 5 min 内 token 被窃取重放 → 由 `authorization_version` bump + `memberRevocations`（backchannel-logout）做长窗口撤销，本轮 §8.2 缓存提供精确到 jti 的撤销 hook
